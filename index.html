Duckle: reviewable DuckDB ETL with an MCP control surface

By André Lindenberg Open original LinkedIn post ↗

Duckle is an open-source ETL tool on DuckDB.

What the Post Claims

The post presents Duckle as an open-source DuckDB-based ETL tool with visual and SQL authoring, CDC, dbt, lineage, JSON pipeline files reviewed through Git, a headless runner, and MCP access that lets agents generate, compile-check, and run the same pipelines. It makes a self-benchmark claim of moving 96 million Postgres rows to Parquet in 39.9 seconds and labels the project Apache-2.0.

The attached product image presents the same positioning: locally authored, server-deployed pipelines stored as one Git file, compiled to SQL on DuckDB, with a no-vendor-cloud/no-per-row-billing/no-lock-in message. It visually depicts connectors for databases, SaaS/apps, warehouses, and DuckDB connectors.

Primary-Source Quick Pass

The guest-visible author comment named github.com/slothflowlabs/duckle; it was inspected directly by network fetch at observed commit 582956dfabbd9d27c8bcc26d6589ecd5d3d5e5ac, without LinkedIn interaction. The public repository, README, both MIT and Apache license files, Rust workspace, MCP and runner crates, benchmark directory, and GitHub Actions workflows were present at that commit.

Project-authored documentation supports a DuckDB ETL product with canvas/SQL authoring, Git-friendly pipeline files, a headless runner, scheduler, roles/audit-log claims, and an MCP server. Its MCP documentation lists discovery, pipeline creation, validation, execution, run-log reading, build, and saved-connection tools. The documented validation path is a compile check before execution, but the same interface exposes run and connection-management operations; a deployment still needs explicit tool permissions, credential scope, data-source/sink review, and human approval for consequential runs.

The repository README documents the 96M Postgres-to-Parquet result and a reproducible-looking benchmark harness, including row-count and sum checks, but this intake did not run the benchmark or independently reproduce its comparisons. Repository CI configuration documents Python contract tests, frontend builds, Rust workspace tests on three operating systems, and database integration jobs; the workflow was inspected but not executed here.

Book Relevance

High relevance for chapters on agent tool interfaces, data-pipeline governance, reviewable automation, deterministic validation, and the boundary between generation and execution.

Candidate claim/example: A useful agent-facing data tool can preserve a reviewable artifact boundary: generate a declarative pipeline, compile-check it without running, inspect its diff and connector scopes, then permit execution only through an explicit approval and least-privilege policy. Git-backed JSON is useful for audit and rollback, but it does not make a pipeline safe by itself.

Hermione Relevance

High relevance. Hermione already separates capture, synthesis, staging, publishing, and queue transition checks. Duckle is a concrete example of why an agent integration should expose a safe planning/validation mode separately from execution, and why data connectors and saved credentials need narrower authority than a text-generation task.

Suggested operational rule: if an agent-facing pipeline service is adopted, allow component discovery and compile-only validation by default; require reviewed pipeline diffs, source/sink allowlists, scoped credentials, bounded schedules, run logs, and a human approval gate before execution or deployment. Treat an MCP server as an execution-capable control plane, not merely a context source.

Evidence and Limitations

Evidence strength: moderate for documented project capabilities; discovery-only for performance, completeness, and operational outcomes. The LinkedIn post and product image are social/project-authored material. The repository and pinned README corroborate that Duckle, its MCP/runner components, license files, CI configuration, and a benchmark harness existed when inspected, but they do not independently validate performance, connector reliability, security, scale, or production outcomes.

The source materials differ slightly in component counts: the post says 366 components, an author comment says 385, and the inspected README describes 384 palette nodes with 366 available. Those counts are time-sensitive project claims and should not be treated as stable capability evidence without a versioned release inventory.

No Duckle package, desktop binary, MCP server, runner, benchmark harness, connector, schedule, or agent workflow was installed or run. No security audit was located or evaluated. Raw guest HTML and authenticated browser artifacts remain local-only and unstaged; visible comments were not expanded, and the complete LinkedIn discussion is not established.
